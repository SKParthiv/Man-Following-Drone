# Man-Following Drone — System Architecture

> **Document Version:** 1.0
> **Status:** Authoritative Architecture — Initial Implementation Baseline
> **Project:** Man-Following Drone
> **Architecture Basis:** Current system architecture defined by the project author

---

# 1. Purpose

This document defines the authoritative software and hardware architecture of the Man-Following Drone.

The system is designed as a **distributed autonomous system** consisting primarily of:

1. A **phone-based high-level computing system**
2. An **ESP32-based real-time flight-control system**
3. A **Wi-Fi communication interface** between the phone and ESP32
4. An **ESC/motor actuation system**

The architecture is intentionally software-driven.

The algorithms, data flow, interfaces, and computational requirements are developed first. Physical hardware and mechanical design will subsequently be derived from the requirements imposed by the software and validated through simulation and testing.

---

# 2. Architectural Principle

The system follows the principle:

```text
Software Architecture
        ↓
Algorithms
        ↓
Interfaces
        ↓
Simulation Requirements
        ↓
Hardware Requirements
        ↓
Physical Design
```

The physical drone is therefore treated as an implementation of the requirements generated by the software architecture.

The architecture is iterative. Results obtained from simulation and physical testing may cause software requirements, interfaces, or hardware requirements to be revised.

---

# 4. Phone — High-Level Computing System

The phone is the high-level computing and autonomy node of the system.

It is responsible for computations that do not require the deterministic real-time behavior of the flight controller.

The phone-side architecture consists of:

```text
Phone Sensors / Android APIs
            │
            ▼
   Phone Sensor Aggregation
            │
            ▼
    Path Finding Algorithm
            │
            ▼
State Reader / High-Level Controller
            │
            ▼
       Phone Wi-Fi
```

## 4.1 Phone Sensor Sources

The phone application will obtain information from the sensors and positioning facilities exposed by the phone operating system.

The currently identified sources are:

* GNSS
* IMU
* Compass / magnetometer
* Phone location information
* Other phone sensor information as required by the algorithms

The exact sensor set and utilization of each sensor remain subject to algorithmic evaluation.

---

# 5. Phone Application

The phone-side system will be implemented as an application running on the phone.

The current implementation direction is a cross-platform C++ application framework, with Qt being the current candidate.

The application will provide access to:

```text
Android Sensor APIs
        │
        ├── GNSS / Location
        ├── IMU
        ├── Magnetometer / Compass
        └── Other required sensors
```

The application will also provide the communication interface required to exchange information with the ESP32 over Wi-Fi.

Android-specific functionality will be used where required by the underlying operating system.

The exact application framework and Android-specific integration mechanism remain an implementation decision and are therefore not considered permanently frozen by this document.

---

# 6. Phone Sensor Aggregation

The Phone Sensor Aggregation component receives measurements from the phone's available sensors and converts them into information usable by the high-level autonomy algorithms.

Conceptually:

```text
GNSS
IMU
Compass
Location
Other Sensors
      │
      ▼
Phone Sensor Aggregation
      │
      ▼
Unified Phone Sensor / State Information
```

Its responsibilities will include, as required by the eventual algorithms:

* receiving sensor measurements
* timestamp handling
* normalization of measurements
* conversion into common representations
* sensor validity handling
* preparation of sensor information for path finding and high-level control

The exact processing responsibilities are **TBD** and must be established before implementation.

Sensor fusion must not be assumed to belong to this component unless required by the architecture.

---

# 7. Path Finding Algorithm

The Path Finding Algorithm is a high-level autonomy component operating on the phone.

Its purpose is to determine the path or movement required for the drone to follow the intended target while accounting for the information available to the system.

Conceptually:

```text
Phone Sensor Aggregation
          │
          ▼
   Path Finding Algorithm
          │
          ▼
Desired Path / Movement
```

The specific path-planning algorithm, representation of the environment, obstacle-handling strategy, and planning frequency are currently **TBD**.

These will be determined during software development and simulation.

---

# 8. State Reader / High-Level Controller

The State Reader / High-Level Controller is responsible for interpreting the current state of the drone and producing high-level control decisions.

It receives information through the phone-side software architecture and communicates desired behavior toward the flight controller.

Conceptually:

```text
Drone State
     │
     ▼
State Reader / High-Level Controller
     ▲
     │
Path Finding
     │
     ▼
High-Level Command
```

This component operates above the real-time stabilization loop.

It does **not** replace the low-level flight controller running on the ESP32.

---

# 9. Phone Wi-Fi Interface

The Phone Wi-Fi Interface provides the communication boundary between the phone and the ESP32.

```text
PHONE
  │
  │ Wi-Fi
  │
  ▼
ESP32
```

The interface will carry information required for high-level control and flight-controller state communication.

The exact communication protocol is currently **TBD**.

The protocol will eventually define:

* message types
* serialization
* timestamps
* sequence information
* update rates
* connection handling
* timeout behavior
* error handling
* failsafe behavior

The communication protocol must be designed independently from the higher-level algorithms so that the software architecture remains well-defined.

---

# 10. ESP32 — Real-Time Flight Controller

The ESP32 is the real-time embedded flight-control node.

Its responsibilities are fundamentally different from those of the phone.

The ESP32 is responsible for:

* low-level sensor processing
* state estimation required for flight
* stabilization
* PID control
* interpretation of high-level movement commands
* generation of actuator commands
* communication with the phone
* real-time safety behavior

The ESP32 must remain capable of maintaining safe local flight-control behavior independently of the phone's high-level computation.

---

# 11. ESP Sensor Aggregation + State Estimation

The ESP32 receives information from the physical sensors required for flight.

The architecture currently identifies the sensor aggregation and state-estimation stage as:

```text
Physical Flight Sensors
        │
        ▼
Sensor Aggregation
        +
State Estimation
        │
        ▼
Drone State
```

The sensor set is determined by the current V1 architecture and may include:

* IMU
* optical-flow information
* ToF altitude information

The exact division between raw sensor processing, aggregation, and state estimation will be defined during implementation.

The resulting state should represent the information required by the stabilization and high-level communication systems rather than unnecessarily transmitting raw sensor streams.

---

# 12. Stabilization / PID Controller

The Stabilization / PID Controller is a real-time component running on the ESP32.

Its purpose is to maintain the aircraft's required physical state and execute the movement commands provided by the higher-level system.

Conceptually:

```text
Desired Motion / State
          │
          ▼
Stabilization / PID Controller
          ▲
          │
      Drone State
          │
          ▼
   Actuation Commands
```

The controller operates independently of the high-level path-finding algorithm.

The specific control architecture, PID loops, control frequencies, gains, limits, and control variables are **TBD**.

---

# 13. Actuation Command Understanding

The Actuation Command Understanding component is the boundary between the flight-control logic and the actuator interface.

It interprets the controller's output and converts it into commands suitable for the ESC interface.

Conceptually:

```text
Stabilization / PID Controller
              │
              ▼
Actuation Command Understanding
              │
              ▼
        ESC Interface
```

The exact ESC protocol and actuator command representation are **TBD**.

---

# 14. ESC and Motor Interface

The final actuation chain is:

```text
ESP32
  │
  ▼
ESC Interface
  │
  ▼
ESC
  │
  ▼
Motor
```

This is a real-time embedded boundary.

The phone is not part of the direct motor-control loop.

Loss of Wi-Fi communication must therefore not directly prevent the ESP32 from executing its local safety and stabilization responsibilities.

---

# 15. Separation of Responsibilities

The system deliberately separates high-level autonomy from low-level flight control.

| Responsibility                   | Phone    | ESP32 |
| -------------------------------- | -------- | ----- |
| Phone sensor acquisition         | Yes      | No    |
| GNSS processing                  | Yes      | No    |
| Phone IMU processing             | Yes      | No    |
| High-level path finding          | Yes      | No    |
| High-level follow logic          | Yes      | No    |
| Wi-Fi communication              | Yes      | Yes   |
| Drone physical sensor processing | No       | Yes   |
| Flight state estimation          | No / TBD | Yes   |
| Stabilization                    | No       | Yes   |
| PID control                      | No       | Yes   |
| Actuator command generation      | No       | Yes   |
| ESC interface                    | No       | Yes   |
| Motor control                    | No       | Yes   |

The table represents the current architectural allocation. Individual responsibilities may later be subdivided into software components without changing the fundamental boundary.

# 16. Communication Architecture

The physical system contains a communication boundary:

```text
┌───────────────┐
│     PHONE     │
│               │
│ High-Level    │
│ Computation   │
└───────┬───────┘
        │
       Wi-Fi
        │
┌───────▼───────┐
│     ESP32     │
│               │
│ Real-Time     │
│ Flight Control│
└───────────────┘
```

ROS 2/DDS will be used as the principal software architecture and simulation communication framework where appropriate.

However, the physical phone-to-ESP32 communication link is a separate interface.

The architecture does **not** require every physical component to communicate through DDS.

In particular:

```text
ESP32 → ESC
```

is a dedicated embedded actuator interface rather than a ROS 2 communication channel.

---

# 17. ROS 2 Role

ROS 2 provides the development framework for the distributed robotics software.

ROS 2 will be used to model and test the computational architecture, including:

* sensor data flows
* state estimation
* high-level control
* interfaces
* simulation
* system integration

ROS 2 topics and other communication mechanisms will be introduced where they represent meaningful software interfaces.

The physical implementation does not need to reproduce ROS 2 internally at every boundary.

The goal is to maintain equivalent **software contracts and behavior**, not to force the same transport mechanism onto every physical component.

---

# 18. Simulation Architecture

Gazebo will be used to validate the software architecture before physical hardware is finalized.

The simulation should reproduce the interfaces required by the algorithms.

Conceptually:

```text
                    SOFTWARE
                       │
             ┌─────────┴─────────┐
             │                   │
          Phone               ESP32
          logic             flight logic
             │                   │
             └─────────┬─────────┘
                       │
                 ROS 2 / Gazebo
                       │
                       ▼
                Simulated System
```

Simulation requirements will be derived from the software.

The physical robot description therefore does not constitute the starting point of the project. It will be developed when the software and simulation require a physical model.

Every major architectural component will eventually be traced through the following chain:

```text

        ↓

        ↓

        ↓
Outputs
        ↓
Data Structure / Interface
        ↓
Implementation
        ↓

        ↓

        ↓

        ↓

        ↓
Path Finding
        ↓
Simulation Test
        ↓

        ↓

```

Similarly:

```text

        ↓

```

This traceability process will be used to prevent hardware selection from becoming disconnected from the software requirements.

# 22. Decisions Currently Established

The following architectural decisions are considered established:

* The system is a distributed autonomous system.
* The phone is the high-level computing/autonomy node.
* The ESP32 is the real-time flight-control node.
* High-level path finding runs on the phone.
* The phone obtains information from its own sensors through the phone operating system.
* The ESP32 performs low-level sensor processing and state estimation required for flight.
* Stabilization/PID control runs on the ESP32.
* The ESP32 directly interfaces with the ESCs.
* Phone and ESP32 communicate through Wi-Fi.
* The phone is not part of the direct ESC/motor control loop.
* ROS 2/DDS is used as the robotics software and simulation communication framework where appropriate.
* The physical phone-to-ESP32 protocol is a separate interface that must be designed explicitly.
* The project will initially remain in a single repository.
* Physical design follows software and algorithmic requirements rather than preceding them.
* `build/`, `install/`, and `log/` are generated ROS workspace artifacts.
* A `scripts/` directory is not part of the project structure.
* Package and implementation details will be introduced incrementally rather than pre-created.

---

# 24. Architectural Rule

The architecture can be summarized by one rule:

> **Define what the system must compute and communicate before defining the physical system that performs the computation.**

The phone, ESP32, sensors, communication system, ESCs, motors, and mechanical structure are implementations of the requirements generated by this architecture.

The architecture therefore serves as the primary reference for subsequent software development, simulation, hardware selection, and physical design.
